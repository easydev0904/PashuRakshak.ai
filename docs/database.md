# Database

PostgreSQL, managed by SQLAlchemy models (`backend/app/models/`) and
Alembic migrations (`backend/alembic/versions/`). Every table has a
`created_at` timestamp; primary keys are UUID strings generated
application-side (`new_uuid()` in `app/db/base_class.py`).

## Tables

| Table | Purpose | Key relationships |
|---|---|---|
| `users` | Farmers, veterinarians, admins | — |
| `farms` | A farm/holding | has many `farm_memberships`, `animals` |
| `farm_memberships` | Which users belong to which farm, with a role | `farms`, `users` |
| `animals` | Registered livestock | belongs to `farms`; unique `(farm_id, tag_id)` |
| `observations` | Farmer-reported daily checks | belongs to `animals` |
| `risk_assessments` | One AI screening result per observation | 1:1 with `observations` |
| `alerts` | Created for MEDIUM/HIGH risk assessments | 1:1 with `risk_assessments` |
| `cases` | Veterinary case workspace | belongs to `animals`; optional 1:1 with `alerts` |
| `case_updates` | Clinical notes / follow-up entries on a case | belongs to `cases` |
| `vaccination_records` | Vaccination history and due dates | belongs to `animals` |
| `education_content` | Prevention library entries | — |
| `audit_logs` | Append-only action log | references `users` (nullable, `SET NULL` on delete) |

## Enums

All enums (`app/models/enums.py`) are defined with **lowercase member
names equal to their string values** — e.g. `UserRole.farmer ==
"farmer"`, not `UserRole.FARMER == "farmer"`. This is a deliberate
fix for a real gotcha: SQLAlchemy's `Enum` column type persists the
Python member *name* by default, not its value. If the member name and
value differ, the database silently stores a different string than
the one the API sends and receives, which is exactly the kind of bug
that only shows up after a round-trip through the database. Keeping
name == value everywhere eliminates the entire class of bug rather
than remembering a `values_callable=` workaround on every column.

## Indexes

Beyond primary keys and foreign keys, the following composite indexes
back the query patterns the app actually runs:

- `animals(farm_id, tag_id)` — unique constraint, doubles as the index
  backing per-farm tag lookups and duplicate-tag rejection.
- `observations(animal_id, observed_at DESC)` — the animal timeline
  and "most recent observation" queries.
- `alerts(status, priority, created_at)` — the vet dashboard's alert
  queue (sorted by priority, filtered by status).
- `cases(animal_id, status)` — case lookups from an animal's profile.

## Migrations

Single Alembic revision today (`cc6d8af7c933_initial_schema.py`),
autogenerated from the models and hand-edited to add the composite
indexes above (autogenerate only creates single-column indexes from
`index=True` on a column; composite indexes are added explicitly in
the migration). Run `alembic upgrade head` from `backend/` to apply.

## Local setup

The dev environment in this repo uses Homebrew PostgreSQL 16 directly
(no Docker available in the dev sandbox this was built in — Docker
Compose is provided and documented for normal use, see
[deployment.md](deployment.md)):

```bash
createuser pashurakshak --createdb
psql -d postgres -c "ALTER USER pashurakshak WITH PASSWORD 'pashurakshak_dev_pw';"
createdb -O pashurakshak pashurakshak
createdb -O pashurakshak pashurakshak_test   # separate DB for the test suite
cd backend && alembic upgrade head
```
